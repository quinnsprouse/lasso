# Guidance: errors, next moves, and guides

Agents fail in two ways: they lack a VALUE (a flag, an id, a token) or they lack a MODEL (what an id looks like, what a replay means, what an output will contain). Lasso answers both at the moment they matter, with one vocabulary, and ships the pieces an agent needs before its first command. Every piece of agent-facing guidance belongs to exactly one of four layers; when adding content, run down this list and stop at the first match.

1. **Shipped skill** (`skills/<bin>/SKILL.md`) — only what must be in context BEFORE any command runs: the safety contract (envelopes, `--json`, exit codes, `transient`, confirmation replay) and an intent router into layers 2 and 3. Size-budgeted (under 4,200 bytes) and checked by `test/contract/skill.test.ts`: every command it names parses, every topic it names exists, and it never restates a topic body.
2. **Generated reference** (`describe --json`, `schema --json`, `describe --command "<name>"`) — syntax, flags, defaults, error codes, envelope shapes, walked from the CommandContracts at request time. Never hand-write anything derivable from a contract; there is no second copy to drift.
3. **Authored guide topics** (`guides/topics/*.md`, served by `guide list` and `guide get`) — the models the surface cannot express: how an id derives from a title, what a token binds, what an output will contain, in which order a workflow runs. Admission test: an agent mid-task would fetch it to build a MODEL, and it would be wrong to bake that model into every error string.
4. **Point-of-use guidance** (`fix`, `next`, `guides` on every terminal outcome) — the complete fix for missing-VALUE failures, the executable next move, and the topic id for missing-MODEL failures. Point-of-use outranks documents in both directions: keep missing-value recovery in `fix` (an error declares no topics of its own for that; it still inherits the command's), and never inline a model that a topic owns.

Contributor docs (this file, `AGENTS.md`, `CONTEXT.md`) are layer zero for the agent editing this repository and never ship to the agent running the CLI.

## Writing a topic

- One file per topic in `guides/topics/<topic>.md`. Frontmatter is exactly `topic`, `title`, `brief`; the body starts with a level-one heading. The generator (`node scripts/guides.mjs`) enforces: kebab-case topic equal to the filename, title 9–88 characters, brief 40–399 characters (the "read this when" synopsis an agent decides on), body 300–12,000 UTF-8 bytes.
- Which commands a topic covers is declared by the contracts (`guides: ["task-ids"]`), never by the topic: one owner per fact. `describe` and `guide list` derive the per-topic command list from those declarations, and a topic no contract declares fails the invariants.
- Every fenced `<bin> …` line in a body is parsed against the command surface by `test/contract/guides.test.ts`; a topic cannot name a flag the parser rejects. A topic that lists flags like a reference also fails: flags belong to `describe`.
- `node scripts/guides.mjs` inlines the Markdown into the committed `src/guides/catalog.generated.ts`, so the single bundled binary carries exactly the topics its version was built with. The Fast profile fails when that file is stale (it is not regenerated by `npm run build`); the guard hook refuses hand edits to it.

## Emitting guidance

- Contracts: `guides` (typed union of topic ids, importance-ordered) and `next: ({ input, data }) => NextAction[]` for the success outcome. `Errors.*` accept `next` and `guides` too. `describe` lists the inventory as `guideTopics` (topic, title, brief, bytes, commands) and each command's ids as `guides`.
- The runtime owns the next moves of its own flows and validates every action with `validateInvocation` (`src/contract/invocation.ts`, the same validator the tests use). An invalid action is dropped into `warnings`: a bad hint after a completed write must not make the write look failed. Tests assert empty warnings.
- A failure a contract raises inherits the contract's `guides` when it declares none; confirmations and dry runs carry them too; a plain success carries only `next`. An error whose `fix` is complete declares no guides of its own (never send an agent to a topic for a missing value).

## Taking it or leaving it

The primitives are optional per command: a contract with no `guides` and no `next` still emits `next: []` and `guides: []`. Removing the guide catalog entirely is only compatible before a derived CLI publishes its surface; afterwards the additive-only rule keeps `guide list`, `guide get`, and the wire fields, normally empty. Before publication, removal touches: `guides/`, `scripts/guides.mjs`, `src/guides/`, `src/commands/guide.ts`, `skills/`, `test/contract/guides.test.ts`, `test/contract/skill.test.ts`, the guide registration in `src/commands/index.ts`, the `GuideTopic`/`isGuideTopic`/`guideInventory` imports in `src/errors.ts` and `src/contract/{contract,surface,adapter,guidance,jsonschema}.ts`, the catalog rule in `.claude/hooks/guard.mjs`, the `guide catalog` step in `scripts/verify.mjs`, the guidance journey and the `skills/` allowlist in `scripts/starter-contract.mjs`, `"skills"` in `package.json#files`; then `rm test/contract/surface.snapshot.json && npm run surface:update` (unpublished) or `npm run surface:update -- --allow-breaking` with a CHANGELOG entry.

Extensions that this template deliberately leaves out, and where to add them: per-command generated topics (a `guide get <command>` alias over `describe --command`), audience variants (an `audience` frontmatter key), and richer next actions (`alternates`, typed inputs to collect) as an additive field on `NextAction`.
